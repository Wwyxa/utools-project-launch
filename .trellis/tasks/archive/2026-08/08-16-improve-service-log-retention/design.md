# 技术设计：项目启动服务日志体验与持久化

## 1. Design Goals

- 保持服务拥有运行日志和进程生命周期的边界，Vue/preload 只负责设置、展示和调用。
- 将实时事件通道与磁盘历史通道分离，避免每条 stdout/stderr 都触发状态文件持久化。
- 让“是否持久化”和保留策略由服务作为唯一事实源，避免前端硬编码和服务启动参数漂移。
- 清除操作必须可确认、可报告结果，并与活动运行的写入器协调。

## 2. Current Boundaries and Failure Points

- `Supervisor.streamOutput` 使用 `bufio.Scanner` 按行读取 stdout/stderr。
- `state.Store.AppendEvent` 当前在同一把锁内更新内存事件、原子重写整个运行状态、追加 JSONL 文件，并执行单文件及全局清理。
- `RuntimeState.Events` 既服务实时事件轮询，又被写入 `state.json`，这会让关闭持久化时仍有输出残留风险。
- `GET /v1/state` 返回运行元数据，历史弹窗再通过 `GET /v1/runs/{runId}/log` 读取完整日志；运行元数据与日志文件的清理目前可能不同步。
- OverlayScrollbars host 会提供横向 flex 布局，因此多条日志必须放在单一内容包裹层内。

## 3. Proposed Data Model

定义服务拥有的日志策略，默认值兼容当前限制：

```text
LogRetentionPolicy
  persist: boolean
  maxCompletedRunsPerProject: integer
  maxBytesPerRun: int64
  maxBytesTotal: int64
```

- 策略写入服务状态并在启动时加载；缺失字段使用兼容默认值。
- 服务内部额外维护全局文件安全上限，不作为用户主要数量语义。
- 运行日志描述信息应包含 `runId`、项目和脚本标识、状态、开始/结束时间、`sizeBytes`、`truncated`、`available`。
- 历史列表使用日志描述信息，而不是单纯使用可能仍存在但没有日志文件的运行元数据。

## 4. Persistence and Event Flow

### 4.1 In-memory live events

- 服务运行期间继续将事件放入内存环形缓冲，满足 preload 的实时轮询和当前终端显示。
- stdout/stderr 事件不因为实时轮询而写入持久化 `state.json`；持久化关闭时尤其不能将输出消息写入状态文件。
- 生命周期事件和运行元数据仍按可靠边界持久化，确保服务重启后可以恢复运行状态。

### 4.2 Buffered durable writer

- 每个活动运行拥有一个长生命周期的 JSONL writer，避免每行 open/write/close。
- writer 按大小或短时间窗口刷新，并在运行结束、服务关闭、清除和策略变化时强制刷新或关闭。
- 允许最后一个刷新窗口内的输出在进程崩溃时丢失，但必须设置截断/不可用状态并暴露持久化错误；不能吞掉错误后继续宣称完整历史。
- 运行状态写入与日志文件写入不再共享每行完整状态重写路径；必要的状态检查点低频批量完成。

### 4.3 Incremental retention manager

- 内存维护活动文件大小、总大小和项目完成运行数量。
- 启动时扫描一次目录并修复索引；运行中只在运行结束、设置改变、达到阈值或周期性维护时扫描/清理。
- per-run 限制使用高低水位：超过上水位时裁剪到低水位，避免每行重写 5 MiB 尾部。若基准显示仍不足，再演进为分段文件轮换。
- 清理顺序固定为：项目数量超限删除项目内最旧已完成日志；总容量超限删除全局最旧已完成日志；最后才裁剪活动日志最新尾部。
- 活动日志始终不因数量限制删除；裁剪后更新 `truncated`，并同步日志描述信息。

## 5. Service API

建议新增经过现有 Bearer token 保护的接口：

- `GET /v1/log-retention`：返回策略、当前总大小、文件数和可选的项目统计。
- `PUT /v1/log-retention`：校验范围、保存策略、执行一次清理并返回实际结果。
- `GET /v1/logs?projectId=...`：返回当前仍可读取的历史日志描述，支持前端按项目展示。
- `POST /v1/logs/clear`：清理所有已完成日志，截断活动日志，清除持久化历史输出，并返回删除数量和释放字节数。
- `GET /v1/runs/{runId}/log` 保持读取单次日志的兼容入口，但增加按尾部/批次读取所需的可选参数或响应分页元数据。

新增接口统一将项目启动服务协议升级到 v2。新版前端遇到旧版服务时显示“服务版本需要更新”，不得把旧服务的 404 当成配置已保存或清理成功。

## 6. Persistence Toggle Semantics

- `persist=false` 时，服务仍保留内存实时事件，但不创建或追加新的持久化运行日志，也不把 stdout/stderr 写进持久化状态。
- 关闭开关不隐式删除旧日志；UI 明确说明旧日志仍存在，并提供清除入口。
- 开启开关后，新运行重新创建持久化日志；已经结束且未持久化的运行不会被补写。
- “清除日志”会协调 writer：先刷新或停止当前批次，删除已完成文件，活动文件截断为零并标记截断，再恢复活动 writer。

## 7. Frontend Flow

- SettingsTab 展示持久化开关、三个策略字段、当前占用量和清除按钮；保存使用显式提交，避免输入过程反复触发清理。
- Terminal history dialog 首次只取得当前项目的可用日志描述，选择某一项后加载最新批次；搜索只作用于已经加载的内容并保持截断提示。
- 历史日志滚动 host 内只保留一个 `min-w-0 w-full` 内容包裹层；行使用时间列和可收缩消息列，保留空格与换行。
- 清除按钮需要确认；成功后刷新历史列表和占用量，不清空实时终端已有内存内容。

## 8. Migration, Compatibility, and Rollback

- 现有状态文件缺少策略字段时，使用当前 5 MiB 单次、100 MiB 总量、200 文件兼容限制，并将持久化开关视为开启。
- 旧 JSONL 文件保持原格式，不做全量重写迁移；新读取器继续接受不完整尾记录并返回截断标记。
- 旧版协议 v1 服务不支持新接口时，前端显示“服务版本需要更新”，不能回退到不受控的本地写入；新状态字段缺失时仍按兼容默认值读取旧 JSONL。
- 批量 writer 可先保留同步生命周期写入作为回滚开关；出现一致性问题时关闭批量输出路径，不改变日志格式。
- 清除和策略更新必须是幂等或可重试的；删除部分成功时返回实际结果并在下次维护继续收敛。

## 9. Security and Data Handling

- 持久化开关关闭时，磁盘上不得新增 stdout/stderr 内容；清除操作还要移除状态文件中的历史输出副本。
- 不改变 stdin 脱敏、环境变量不持久化、服务令牌不进入事件的现有约束。
- 所有新接口复用现有 loopback、token、请求体校验和路径验证。
