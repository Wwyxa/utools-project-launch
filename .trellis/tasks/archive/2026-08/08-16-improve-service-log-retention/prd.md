# 改进项目启动服务日志体验与持久化

## Goal

让项目启动服务的历史日志可读、可控、可清理，并让用户明确选择是否将运行输出持久化到磁盘；高输出任务不应因为逐行持久化而明显拖慢子进程或造成不必要的磁盘写放大。

## Background

- 历史日志弹窗中的日志行横向排列，长文本被压缩成逐字竖列，当前布局无法正常阅读。
- stdout/stderr 由 [service/internal/process/supervisor.go](../../../service/internal/process/supervisor.go) 按行接收；当前每行都会触发运行状态原子写入、日志文件追加和完整日志目录配额检查。
- 当前保留限制是单次 5 MiB、全部日志 100 MiB、最多 200 个日志文件，且由 Go 常量固定，前端只展示硬编码文案。
- 当前运行元数据最多保留 200 条，历史列表可能展示已经被日志容量策略删除的运行，用户点击后才得到不可用错误。
- 历史读取会一次性读取并渲染整个保留文件，需要在保留可查看能力的同时控制渲染成本。

## Requirements

### R1. 修复历史日志查看体验

- 历史日志必须按时间顺序纵向排列，每条记录的时间和消息内容保持稳定的列布局。
- 长命令、路径和无空格输出不得把其他日志列挤窄；日志缩进和换行应尽量保留。
- 历史列表只显示当前项目仍有可读取日志的已完成运行，并展示状态、时间、大小和是否截断等必要信息。
- 历史日志支持搜索，并提供复制日志和清晰的加载、空数据、截断、不可用状态。
- 大日志查看不能一次创建不可控数量的日志 DOM 节点；应支持从最新输出开始按页或按批次读取。

### R2. 提供持久化开关

- 用户可在项目启动服务设置中选择是否持久化运行输出。
- 持久化关闭后，新的 stdout/stderr 不得写入运行日志文件或持久化运行事件；服务运行期间仍可正常提供实时日志。
- 现有安装升级后默认保持当前行为，避免静默改变用户已有的日志保留方式。
- 关闭持久化不自动删除已有文件；界面必须明确提示已有日志仍会保留，用户可通过“清除日志”主动删除。
- 服务重启后，关闭持久化期间产生的输出不应重新出现在历史日志中。

### R3. 支持用户配置保留策略

- 日志数量以“每个项目最多保留多少次已完成运行”表达，不采用用户不可感知的全局数量作为主要设置。
- 单次运行大小和所有项目总大小都可配置；活动运行不计入数量上限，但计入总大小上限。
- 超过项目数量限制时，优先清理该项目最早的已完成日志；超过总大小限制时，优先清理所有项目中最早的已完成日志。
- 活动日志不能因数量限制被删除；在总大小不足时只保留最新的完整输出，并标记为已截断。
- 后端保留独立的全局文件安全上限，防止大量极小日志在多个项目间产生失控的文件数量；该上限不替代用户可见的项目数量配置。
- 设置更新后应一次性应用清理，并向用户反馈新的策略和当前使用量。

### R4. 提供一键清除日志

- 用户可从日志历史或服务设置进入“清除日志”操作，并看到确认提示。
- 清除操作删除所有已完成运行的持久化日志；活动运行的持久化文件被清空并继续接收后续输出，实时终端内容不被清空。
- 清除操作同时移除持久化状态中的历史输出，避免文件删除后输出仍残留在状态文件中。
- 操作结果返回删除的日志数量和释放的字节数；失败时不能假报成功。

### R5. 降低持久化写放大

- stdout/stderr 不能再对每一行执行完整状态文件原子写入和全目录配额扫描。
- 运行日志应使用按大小或时间触发的批量写入，并在运行结束、服务关闭和明确清理边界执行必要的刷新。
- 配额清理应使用内存中的大小跟踪，并仅在启动、运行结束、配置变化或跨越阈值时执行。
- 单次日志达到上限后不得在每一行都重写完整的保留尾部。
- 即使批量持久化失败，实时日志和服务进程控制仍应保持可用，并向状态或诊断路径暴露错误。

### R6. 保持兼容和安全边界

- 既有日志 JSONL 文件仍可读取，旧版状态文件升级后不会丢失可读取的保留日志。
- 服务令牌、完整环境变量、输入秘密和凭据不得进入新的持久化路径。
- 服务关闭、重启、异常退出和活动运行恢复场景都必须保持日志文件与运行元数据的一致性。

## Key Product Decisions

- 持久化开关默认值：现有安装和首次启用服务均默认开启，以保持当前功能；用户可以主动关闭。
- 关闭持久化的行为：只影响后续输出，不自动删除已有日志；删除由用户明确触发“清除日志”。
- 数量语义：用户设置按项目计算已完成运行数；总大小按全部项目计算。
- 清除范围：清除历史持久化内容，不影响实时终端显示和活动进程。

## Acceptance Criteria

- [ ] 在桌面和窄窗口下，历史日志按行纵向显示；长路径、长命令和多行输出不会出现横向日志列或逐字竖排。
- [ ] 历史列表不再展示已被清理、无法读取的日志条目；读取失败时显示可解释的错误状态。
- [ ] 用户关闭持久化后，新运行的输出只存在于服务运行期间的实时通道，不产生历史日志文件，重启服务后也不可见。
- [ ] 用户可配置每项目数量、单次大小和总大小；调整后清理顺序符合项目级数量和全局容量规则，活动运行保持可控。
- [ ] 用户确认一键清除后，已完成日志和持久化历史输出被移除，活动日志被清空且实时输出继续工作，并显示实际清理结果。
- [ ] 高输出运行不再逐行重写状态文件、逐行扫描日志目录或逐行重写完整日志尾部；新增基准或诊断检查能证明写入批处理生效。
- [ ] 服务重启后，开启持久化的保留日志仍可读取，截断标记、大小和运行归属正确。
- [ ] `go -C service test ./...`、`go -C service vet ./...`、`npm run lint`、`npm run build` 及相关桥接检查通过。

## Out of Scope

- 不引入外部日志平台、数据库或跨设备日志同步。
- 不改变服务模式的默认关闭、进程归属、自动化调度和秘密脱敏规则。
- 不为单个脚本或单个任务增加独立于项目的持久化策略。
- 不在本任务中重做实时终端的全部交互，只修复与历史日志共享的布局和持久化边界。

## Risks and Deferred Items

- 批量写入会允许服务崩溃或断电时丢失最后一个刷新窗口内的少量输出；生命周期状态仍应优先可靠落盘，并在界面提示历史可能截断。
- 新增配置和清除接口统一升级项目启动服务协议到 v2；旧版已安装服务必须显示需要更新，不能让新版前端静默调用旧接口。
- 历史日志分页会增加 API 和前端状态复杂度；MVP 可先按最新尾部批量读取，完整虚拟滚动作为性能验证后的后续收敛项。
